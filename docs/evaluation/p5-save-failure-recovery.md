# P5：保存失敗から、現在の訂正を守って回復する

保存が失敗したときに、以前の保存版と、まだ保存できていない現在版を混同しないための変更です。最後に保存できたr1はIndexedDBに残し、現在のr2と未適用フォームは画面のメモリ内に保持します。現在版を退避した完全JSONは、元の保存を上書きしない別コピーとして復元できます。

**完全JSONに未適用フォームの下書きは含まれません。** 完全とは、適用済みProjectの原文・参照・旧版・履歴などを含むという意味です。実名や機密情報も含まれるため、保管先への注意を画面に表示します。

## 利用者に見える違い

- 現在版が保存済みか未保存かと、最後に保存できた版の時刻を分けて表示します。初回保存前は「まだ保存していません」と表示します。
- 保存失敗時は成功通知を消し、エラーを表示します。追加の復旧欄に「現在の訂正」と「最後に保存した版」の別々の完全JSON操作を置きます。初回保存に失敗した場合、後者は利用できません。
- 通常時は既存の出力ダイアログを維持します。「全体・JSON・仮名化なし」でも現在版を退避できます。専用ボタンが以前なかったことを、復旧経路そのものがなかったとは扱いません。
- 原文下書きに加え、分類・話者・理由・所属先の詳細フォームもメモリ内に保持します。詳細を閉じ、同じ発言を開き直しても再開できます。復帰線を外す承認は以前どおり再確認し、下書きから自動再承認しません。
- 振り返り・欠落申告・原文対応・問いと根拠・発言境界の未適用入力は、それが消える画面切替やProject切替の前に確認します。Projectの変更をまだ一度も適用していなくても確認対象です。再読込・タブ離脱にはブラウザ標準の離脱警告を使います。

## 観点を比べて決めたこと

**データの完全性。** IndexedDBの要求とトランザクション完了は別のPromiseです。`put`の失敗だけを捕捉する実装では、完了側の拒否を観測できませんでした。完了Promiseを要求より先に取得し、要求失敗・abortの両方を処理します。既にabort済みのトランザクションに再びabortを要求した場合も、元の失敗理由を失いません。

**操作の連続性。** 詳細を閉じるたびに下書き破棄を尋ねる方式は、既存のEscape操作を変えてしまいます。詳細フォームはメモリに保持する方式を選び、保持しない関連フォームでは破棄直前に確認します。振り返りフォームも、単に閉じて再開した場合や、無関係な端末保存で下書きを失わないようにしました。

**モバイルの使いやすさ。** 復旧欄の常時表示は通常時のキャンバス寸法に影響しました。専用欄は保存失敗時だけに限定し、それ以外は既存出力を使います。通常のタッチ操作の回帰テストも維持します。これは実機iPhoneなどの認証を意味しません。

**復元の独立性。** 別コピーは新しいID、`saved: false`、`storageRevision: 0`で開始します。元の保存世代を持ち越して別コピーの初回保存を競合扱いにする問題を防ぎます。明示保存後の世代は1です。

**容量と処理時間。** 50MiB・1,000履歴などの閾値は変更しません。大きな履歴を繰り返しシリアライズする処理を削減し、同一検証内の容量集計を再利用します。保存時は正規化後に検証し、保存世代フィールドの新設や桁増加でサイズが増える場合にはトランザクション内で再検証します。同じ桁数の世代更新はJSONのバイト数を変えません。実際のUTF-8 JSON長との一致も検証します。

## 保存失敗の受入条件

[`save-failure-recovery.spec.ts`](../../e2e/save-failure-recovery.spec.ts)は、保存済みr1がある場合・初回保存前のそれぞれで、`put`のquota失敗とトランザクションabortを別々に注入します。

保存済みr1がある場合は、r2を適用し、さらに話者・分類・理由の未適用下書きを入力してから保存を失敗させます。その後、次の条件を比較します。

1. 成功通知がなく、未保存状態とr1の最終保存時刻が表示される。保存ボタンからエラーへフォーカスを奪わない。
2. IndexedDBのr1は全体、保存世代、時刻、履歴とも変わらない。部分保存がない。
3. r2と下書きはメモリに残る。キーボードで完全JSONをダウンロードしても下書きを適用・破棄しない。詳細の閉鎖・再開でも残る。
4. 現在版のJSONと最後の保存版のJSONを別々に取得できる。現在版にはr2の履歴があり、未適用下書きはない。
5. 原文版、coverage、非空の字幕cue台帳・lineage・問い、欠落申告、関係、問いのグラフ全体を比較する。話者ラベルと原文も仮名化しない。この障害マトリクスの応答・根拠配列は空であり、それらの非空の永続化をここで新規実証したとは扱わない。非空の詳細状態には既存の`rich-persistence.spec.ts`の別試験がある。
6. コピー切替をキャンセルすれば現在版と下書きを維持する。意図的な再読込では、保存できていないr2を保存済みとして復活させない。
7. JSONを別コピーへ復元し、未保存・別ID・世代0を確認してから保存する。元r1を変えず、コピーの履歴と来歴を保持する。そのコピー上のUndoでも整合する。

初回保存の失敗では、保存レコードが0件のままであり、保存時刻や最後の保存版を捏造せず、現在版を退避して別コピーに保存できることを確認します。いずれもページの未処理エラーがないことを確認します。

別の自動保存試験では、入力中の理由欄にフォーカスを置いたままquota失敗を発生させ、下書き・フォーカス・r1を保持することを確認します。障害を解除して次の訂正が自動保存された後は、古い保存失敗の表示と復旧欄を解消し、実際に保存した版の時刻へ更新することも確認します。

[`draft-recovery-guard.spec.ts`](../../e2e/draft-recovery-guard.spec.ts)は、保存済みProjectでフォームだけが変更されている場合のコピー・画面切替、振り返りの開閉・無関係な保存、問い・境界編集の下書きを確認します。既存のEscape、IME、原文下書き、Undo、所属変更、lineage拒否のテストは削除しません。

## 容量とトランザクションの境界

[`p5-capacity-boundaries.test.ts`](../../tests/p5-capacity-boundaries.test.ts)と[`p5-storage-failure.test.ts`](../../tests/p5-storage-failure.test.ts)で次を確認します。

- 完全JSONが50MiBちょうどなら検証・出力でき、1バイト超過は拒否する。
- 保存時の正規化後も50MiBちょうどを保存でき、1バイト超過ではDBも呼出元も変わらない。
- 保存世代が9から10に増えて1バイト超過する場合、`put`前にabortし、既存保存と呼出元を維持する。
- 現行入力の文字数・ファイル数を増やさず、旧版原文だけが増えた場合も完全バックアップの容量に含め、50MiB超過を拒否する。
- 1,000履歴を許可し、1,001履歴を拒否する。UTF-8、日本語、絵文字、引用符、改行、不正サロゲートも実シリアライズのバイト長と照合する。
- quota要求失敗、`put`後のabort、要求失敗とabortが重なる場合に、初回保存・既存r1の双方で部分commitしない。完了Promiseを必ず観測し、呼出元を変更しない。

変更前には、要求失敗とabortが重なる試験で完了Promiseが観測されず、50MiBの検証・出力試験は既存の5秒制限に達しました。閾値・既存アサーション・テスト時間制限を緩和せず、要求／完了の処理漏れと巨大JSONの重複集計を修正しています。

## G5は未完了のまま

ここでのquotaとabortは決定的な障害注入であり、実端末の容量逼迫を実測したものではありません。ブラウザ自動化のキーボード確認は、実支援技術による確認の代替でもありません。フォーム下書きはメモリ内の保持であり、警告を承認して再読込した後まで復元できるとは案内しません。

実機・実GPU、実支援技術、対応OSとブラウザ、OSキャッシュやホスト負荷の統制、実AIの日本語品質は未計測の項目を残します。今回の局所的な保存復旧試験や既存のソフトウェア性能試験だけで、G5全体を完了扱いにしません。
