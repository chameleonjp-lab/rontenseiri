# 原文訂正の自動保存・リロード・Undoの限定試験

## 今回確認すること

統合要件v0.4の[R15](../requirements-and-development-plan.md#r15-訂正の影響がある結論を更新するか要再確認にする)と、P5の訂正状態の保存・復旧に対する1本の通常UI経路を追加する。製品コードは変更しない。

`e2e/r15-correction-reload-undo.spec.ts` は、異なるTXT原文を持つ根元R・依存先A・無関係なBの3議題を、完全JSONの通常復元UIから用意する。R→Aは明示依存1本で、AI解析結果や自動的な意味判断の証拠ではない。

1. 明示保存でIndexedDBの初回保存版を作る。
2. Inspectorの「発言・原文」から否定を追加する訂正を保存する。その後は明示保存せず、通常の自動保存を待つ。
3. IndexedDBを読み取り専用で観測し、R/Aの`needsReview=true`、Bの`false`、別原文の発言・旧原文版・関係・到達点の保持を検査する。原文版と引用オフセットの一致、履歴1件、保存世代の増加も確認する。
4. `page.reload()`で画面とモジュール状態を破棄し、「最近の作業」から保存版を開く。R/Aには到達点と要再確認警告が併存し、Bには警告が出ないことを検査する。完全JSONのプレビュー内容を訂正後のDBレコードと照合する。
5. 通常の訂正履歴UIで1回Undoし、自動保存を待つ。発言・議題・関係は訂正前の値へ戻り、原文版カタログと訂正記録は削除されず、Undo記録が正しい訂正IDを指すことを確認する。
6. 再度リロード・最近の作業から再開する。3議題に訂正影響の警告がなく、引用が旧版に戻り、完全JSONがUndo後の保存内容と一致し、追加Undoが無効であることを確認する。

## 証拠の読み方

初期DB、訂正後DB、訂正後リロードの完全JSON、Undo後DB、Undo後リロードの完全JSONをPlaywrightのJSON attachmentへ残す。DBへの書き込み・訂正・Undo・再開はすべて製品の通常UIで行い、テスト側のブラウザ評価はnative IndexedDBの読み取りだけに使用する。保存関数の直接呼出し、保存成功のstub、状態の注入は行わない。

保存内容と完全出力の比較では、ナビゲーションの`selectedAgendaId`と保存メタデータの`saved`・`storageRevision`・`updatedAt`だけを除く。それ以外のfixture内データを深く比較する。保存フラグと保存世代は別のassertionで検査する。Undoの意味的復元は発言・議題・関係を訂正前と比較し、原文版カタログは訂正後の追記状態を維持することを比較する。全フィールドの独立した期待値や、任意Project全体の完全復元を証明するものではない。

完全SHAの実行証拠は当該Draft PR本文と同じSHAのCI artifactに対応づける。初期開発中の失敗や旧SHAの結果を最終SHAの成功証拠へ読み替えない。

## 対象外として残すこと

- #24の図・原文一覧等の訂正UI全般の重複検証や、#29/#30の反復訂正・多段Undo・分岐の網羅は行わない。
- JSON復元fixtureを起点とする。空の作業からの依存関係作成UI、実AI、実モデルの意味品質は検査しない。
- 1本の明示依存・3原文・1訂正・1Undoのみ。問い版・応答・根拠・解釈候補の混合依存、複数依存、字幕cue、lineage、実解析runを含む状態はこの試験の証拠ではない。
- 完全JSONはプレビューを検査する。ファイルのダウンロードや訂正後JSONの再インポートは含まない。
- 保存失敗・競合・別タブ・強制終了・保存途中のリロード・保存容量・性能・ピークメモリは検査しない。
- desktop viewportの開発用headless Chromiumに限定する。production/offline、スマートフォン、実OS、支援技術、キーボードのみの一連操作の受入ではない。

R15全体、G5全体、G0–G8の受入完了を宣言しない。先行Draftのマージも仮定を超えて主張しない。
