# 復帰先に入る複数の線を安全に訂正する

## 確認した不足

基準HEAD `2c62fade33cb90d63348e2e1c6a33cbd7d607c0b` のInspectorは、復帰先の分類を本筋以外へ変える際、`relations.find`で最初の始点だけを説明していた。一方、解除は対象に入る全復帰線について、始点単位の`correctReturn`を繰り返していた。このAPIは同じ始点から出る復帰線をすべて消すため、別の復帰先への線まで失う可能性があった。現行スキーマは同じ始点から複数の復帰線を持つ状態を受理するため、単なる仮説上の不正データではない。

これは関係の種類・根拠・表示省略を誤読させない計画（R10・R20）に対する実際の説明・API境界の不足である。新たな一括編集画面を広げるのではなく、既存の分類変更時の「保持／全解除」操作を修正する。

## 修正の契約

Inspectorは選択した発言に入るすべての復帰線を表示し、各始点／終点、関係ID、全根拠IDと原文を列挙する。同じ始点から別の復帰先へ向かう線も「解除対象外・保持」として同じ形式で説明し、根拠が空の場合は未登録と示す。分類変更時の選択はその一覧の全件に適用されると明示し、未選択では保存しない。復帰線の集合や根拠が変わった際は選択をリセットするが、無関係な保存で下書きは消さない。

`clearIncomingReturns`は、`kind=return && to=対象ID`に一致する線だけを取り除く。該当始点は「なし」ではなく「未確定」にする。同じ始点から別の復帰先へ向かう線、別の始点／終点の線、同じ終点への別種の線はID・順序・根拠を含めて残す。単独APIは1件の訂正、分類変更との同時保存もInspectorで1件の訂正になり、1回のUndoで復帰線のID・順序・根拠と発言・議題を復元する。

## 回帰で固定するもの

共有fixtureは1つの復帰先に2本の復帰線を入れ、対象外の線を配列中に挟む。同じ始点の別の復帰先、別種の線、異なる根拠配列を含める。単体試験は限定解除、非破壊性、1回のUndo、JSON往復後のUndo、理由・対象・空操作の拒否を確認する。実UI試験は全件の説明、未選択での拒否、全解除と保持の両選択、IndexedDBへの保存、Undo後の厳密配列比較と再開を確認する。

## 負例による検出確認

新しい対象限定解除の単体assertを旧始点単位ループに適用すると、残すべき `incoming-fixture-return-u03-u09` が消えて失敗した。製品の200msゲートや既存テストは変更していない。UI試験初回はChromium実行ファイル不在で起動前失敗し、実在する `/usr/bin/chromium` を明示して解消した。その後、新規試験のfieldset指定が複数要素に一致したため名前付きgroupへ限定し、assert内容は維持した。これらの開発時失敗を最終SHAの検証結果と混ぜない。

## 証拠の区別

独立レビューは静的なコード確認であり、試験実行の証拠ではない。最終SHAでの試験結果はPR本文に記録する。基準HEADの199単体・50機能E2E成功等は、新しいHEADの結果に流用しない。

旧SHA `5b0ac40129ded26a1cff844d7de5937c7f866b12` のdev性能失敗（selection p95 249.9ms／search p95 296.7ms）は証拠を変更せず別扱いにする。元実験を再実行せず、原因未確定を維持する。本番の限定性能試験や今回の安全性回帰が成功してもG5全体の完了ではない。`eligibleForG5=false`を維持する。

## 追加確認：根拠本文の変更後は再承認する

`472926d` に対して、同じInspectorで分類の下書きを本筋以外にし、解除を選択した後、原文モードで根拠にも使われている選択発言の本文を保存し、分類モードへ戻る実UI回帰を実行した。表示原文は更新されるが解除選択は残ることを、`not.toBeChecked` の失敗として確認した。最初のレビュー段階の疑義を、そのまま製品不具合と断定したものではない。

安全側の契約として、確認選択をリセットする署名に、対象線・同じ始点の保持線の関係情報だけでなく、画面に表示した全根拠本文を含めた。関係ID・根拠IDが同じでも本文が変われば保持／解除の両方が未選択になる。更新された原文を示し、再選択前の分類保存を拒否し、線を一切消さないことを実UI回帰で固定する。利用者の分類下書きと変更理由は維持する。

## 追加確認：分割試験の保存完了を厳密に待つ

旧push CI `39097958704`（SHA `472926d`）は単体・build・audit等が成功した後、機能E2Eの `split-evidence.spec.ts` のleft経路で失敗した。reload後の `.recent-open` が5000ms内に現れず、機能段階は48成功／1失敗／1 skip／後続serial3件未実行、offline・benchmark・両性能段階はskipだった。同じSHAのPR CI `39097961554` は成功しており、両結果を混ぜない。

元試験の `status` に「保存」を含むという待機は、復元直後の「元の保存は上書きしていません」という通知にも一致する。保存の確定前にreloadし得る明確な試験プロトコル上の競合がある。これだけで元失敗の唯一の原因や製品の永続化欠陥がないことまでは断定しない。

修正後は完了通知を厳密に待ち、さらにreadonlyトランザクション完了後のIndexedDBから、保存フラグ・保存revision・元発言の消失・分割先2件・全3解釈参照の厳密な移送先と状態を確認してからreloadする。別コピー復元で新しいproject IDになる契約に合わせ、fixture固有の作業名で保存レコードを照合する。left経路では実writeトランザクションを試験のゲートで保持し、解放前に保存完了通知が出ないことも確認する。固定sleepやタイムアウト延長、既存の復元後／Undo後assertの削除は行っていない。

旧push runはrerunせず、ログ・artifactメタデータを保存する。不完全なZIP取得物は完全なartifactとは呼ばない。`472926d` のローカル本番測定は追加修正が必要になった時点で中断し、完了済み・途中rawと中断理由を保存した。未完了を9群成功とは記載しない。新しい最終SHAで全検証を実施し直す。
