# 論点整理ツール：統合要件・開発計画 v0.3

更新日：2026-10-17  
対象リポジトリ：[chameleonjp-lab/rontenseiri](https://github.com/chameleonjp-lab/rontenseiri)  
状態：要件・設計・実装順をまとめたレビュー用計画。アプリの実装、モデル採用、性能・精度検証、サイト公開は未実施。

v0.2 の全18章を引き継ぎ、最新の方針に合わせて、入力を文字起こし済みドキュメントとテキストに限定した。第16章は設計判断と検証ゲート、第17章は成果物・依存関係・受入条件を持つ段階計画に具体化した。文書内の数値は、断りのない限り提案する初期上限・合格目標であり、達成実績ではない。

この変更は計画文書1件の追加を対象とする。既存 README の変更、アプリ実装、マージ、本番配備を含まない。ソダテルモンとは別プロジェクトとして扱う。

## 1. 目的・設計の軸

会話の始まりから終わりまで、何が問われ、何が答えられ、どの発言で論点が変わり、何が置き去りになったかを可視化する。

話すうまさ、強い口調、揚げ足取り、「論破」の印象と、主張の内容・根拠・筋道を分けて確認できるようにする。意見の変化も、そのきっかけとともに会話の成果として残す。

話題が広がること自体を問題とせず、掘り下げと論点のずれを区別し、元の問いに戻れるようにする。討論、会議、記者会見、日常会話、動画・切り抜きから別途作成された文字起こしの検討を想定する。元メディアの内容を直接確認したことにはしない。

AIが人の意図や正しさを最終判定する道具にはしない。原文、分析、推定、確認済みの説明を分け、誰でも根拠を確かめて訂正できることを重視する。

## 2. 今回決まった提供方針

- 無料で利用できるオープンソースを目指す。
- GitHubでソースを公開し、GitHub Pagesで普通のWebサイトとしてアクセスできる構成を目指す。
- 利用者にGitHubの知識、アカウント、プログラミング操作を要求しない。
- 利用者自身のブラウザ・端末内で、文字起こし済み文書の読み込み、AI解析、図の生成を行う。
- 運営側が全利用者分の有料AI API費用を負担する構成は基本方針にしない。
- 外部AIとの手動のコピー往復や、個人API契約を利用の前提にしない。
- 無料とは、サービス利用料や有料API解析料を要求しない方向を指す。端末の計算資源・電力・通信・ストレージは利用する。
- 古い端末の救済は現時点では優先しない。具体的な対応環境は検証して明示する。
- フォークや改善提案を受け、更新して育てられる構成にする。

ブラウザ内のテキスト解析は WebLLM を第一候補とし、Transformers.js／ONNX Runtime Web を比較候補とする。いずれも正式採用は第16章の日本語品質・端末負荷・ライセンス検証を通過してから決定する。これらのライブラリの存在は、本ツールの要求精度・速度・容量が満たせる証拠ではない。音声認識・文字起こし機能には利用しない。

## 3. 画面と基本操作

ホーム → ファイル読み込み → 解析・生成中 → 結果の分岐図 → 発言一覧や詳細、という流れ。

### ホーム
- 「新しく始める」を主要な入口とする。
- 使い方・説明への入口を置く。詳しい説明は別画面にする。
- 最近の作業への導線は追加候補であり、保存方式と併せて検討する。

### 読み込み
- 入力は文字起こし済みの文書・テキストと、テキストの貼り付けに限定する。形式・上限・導入順は第16・17章に定める。
- 音声・動画の読み込み、録音、再生、取得、文字起こし、話者の声による識別、画像OCRは対象外。URLからのメディア・字幕・文書取得も行わない。
- 「アップロード」より「端末からファイルを読み込む」など、外部送信しない実際の動作に合う表現を使う。

### 解析中
- 文書検査・テキスト抽出、モデル準備、議論の整理など進行段階を表示する。
- 曖昧な話者・分岐のたびに利用者へ質問して処理を止めない。
- 判別できない情報は不明・推定として保持し、結果生成後に修正できるようにする。
- 実行不能なエラーまで成功扱いで進める意味ではない。失敗内容と再開方法の扱いは別途設計する。

### 結果
- 最初は分岐図を表示する。一覧を初期表示する案から変更済み。
- 図から該当する発言一覧へ、一覧から図へ双方向に移動できる。
- 発言、分岐、結論から読み込んだ原文・文書内の該当位置にたどれる。入力に時刻・出典リンクが含まれる場合は参照情報として保持するが、アプリはリンク先を取得・埋め込み・再生しない。

## 4. 原記録・登場人物

- 発言ごとにID、話者、順序、入力に含まれる時刻、文書ページ・行・段落等の位置を保持する。出典メディアの時刻も利用者が提供した参照情報としてのみ扱い、真偽・同期精度を自動検証しない。
- 誰が誰に、どの問い・発言に応答したかを結びつける。
- 引用された言葉と、引用者自身の主張を区別する。
- 話者不明、原文中の「聞き取り不明」等の表記、記録範囲の不足を明示し、訂正できる。
- 原文は分析で上書きしない。
- 相槌等は削除ではなく表示を畳む。「はい」を一律に同意と解釈しない。
- 人物は名前やラベル等で識別し、色だけに頼らない。
- 文字起こしの誤りと、原発言の内容を混同しない。

## 5. 問い・回答・主張の構造化

- 複数の問いを含む質問は分解する。
- 質問者が求めた回答と、回答者が答えた対象を照合する。
- 主張、立場、理由、根拠、前提、条件、対象範囲、用語の意味を分ける。
- 賛成、反対、明示的中立、判断保留、条件付きの立場、表明なし、二択の前提への異議を区別する。
- 理由だけ述べた人を、自動で中立や賛否のどちらかに分類しない。
- 回答の有無と、問いの解決を区別する。
- 「できる」が技術・費用・期間のどれを意味するかなど、定義や条件の違いを追跡する。

## 6. 大きい問い・小さい問い・分岐図

- 最初の大きい問いを常に確認できる位置に残す。
- 議題を開くと、前提、用語、条件が一覧で見える。
- 大きい問いに付随する小さい問いが複数生まれる構造を表現する。
- 小さい問いには「元の問いの何を検討しているか」と回答状況を付ける。
- 同じ問いの掘り下げ・派生は同じブロック内で整理し、新しい問いは分岐として扱う方向。
- 小さい問いが発生したこと自体を脱線と判定しない。
- 元の問いとの関係が薄くなったり、必要なつながりが示されていない箇所を、根拠付きの分析として示す。
- 枝の深さや数を、そのまま論点のずれの大きさにしない。
- 問いだけでなく、分岐の根拠になった発言も図から確認できる。
- 話題の継続、分岐、復帰、合流を表す。
- 元の問い、分岐した発言、移った先、元の問いに残った未回答を対応づける。
- 着目する問いを変えてたどれるようにし、図の中央を「正しい主張」と見せない。

「派生」と「別の問い」の実際の判別はAIが自動で行い、根拠を付ける。判定基準と精度は検証し、利用者が修正できるようにする。

## 7. 解釈・意見の変化

- 各参加者が何を尋ねられた／答えていると理解していた可能性があるか、解釈候補を示す。
- 根拠の発言と結びつけ、複数の読み方は残す。
- 発言記録、AIの推定、本人が確認した説明を区別する。
- 質問者自身が問いや考えを変えた場合も追う。
- 立場の変化の前後と、きっかけ候補の発言を結ぶ。
- 時間的に後だったことだけで、原因と確定しない。
- 推定した原因と、本人が明言した理由を区別する。
- 後からの説明、訂正、撤回は追加履歴にし、当時の発言を消さない。

## 8. AIの分析と確認の助言

- 原文とは別に、未回答、回答対象のずれ、前提不足、用語・条件の変化などを示す。
- 「逃げようとしている」等の心理を断定せず、具体的な発言と問いの関係を示す。
- 質問側にも同じ基準を適用する。未確認の前提の押しつけ、要求の変更を扱う。
- 言い間違いの訂正と、主張の結論への影響を分ける。
- 話し方が不得手な人も同じ形式で整理するが、述べていない理由や根拠を足さない。
- 次に何を確認すれば議論がつながるかを提案する。
- 記録、解釈、確認の提案を見た目でも区別する。
- リアルタイム分析は将来候補に留め、初期版では実装しない。将来検討する場合も対象は追加入力されたテキストとし、録音や音声認識の導入は本計画に含めない。推定による指摘で議論を不当に遮らない。

## 9. 合意と外部の妥当性

- 誰が何に、どんな条件で合意したかを記録する。
- 沈黙や相槌のみで合意を確定しない。
- 参加者の合意と、結論の正しさ・妥当性を分ける。
- 事実の裏づけ、法律、倫理、第三者への影響、世論を別に扱う。
- 多数派の意見を事実の正しさと混同しない。
- 根拠の未提示を虚偽と断定しない。
- 価値観の相違を論理の誤りと扱わない。
- 公平さを、双方の根拠の強さが同じという意味にしない。
- 外部資料による検証には出典・対象時点・確認範囲を残す。

初期版は外部検索・自動事実確認を行わない。利用者が別途確認した資料の本文、出典URL、対象時点、確認範囲を端末内で追加できる。資料内での支持・反証候補と、利用者による確認の記録を分ける。モデルの知識のみで検証済みにしない。リンク先の現在性・真偽、法律・医療等の専門的妥当性は本ツールでは保証しない。

## 10. 最終まとめ

- 全体で扱われた問い、到達した結論、残った疑問を一覧化する。
- 回答状況、合意・対立状況、外部検証状況を別軸で示す。
- 回答あり、一部回答、未回答、保留、対立したまま終了などを区別する。
- 「回答がある」「合意した」「解決した」「裏づけがある」を一つの状態にまとめない。
- 残った問いには不足情報と、次に確認するとよいことを添える。
- まとめから該当する分岐・原文・根拠へ戻れる。

## 11. 漏れ・誤分析への対処

- 原文の各発言が、図や分析結果のどこに反映されたか逆引きできる。
- 未反映の発言を確認できる。
- 利用者が「この一言が重要」と指定して拾い直せる。
- 話者、解釈、分岐等の訂正と履歴を保持する。
- 完全に漏れないと保証するより、見落としを発見して修正できる設計にする。
- 人が確認した会話と照合し、重要発言の見落とし、誤った分岐、誤った話者帰属等を検証する。

## 12. ローカル処理・保存・通信

- 入力文書、文字起こしテキスト、分析結果を運営側・モデル提供元・外部AIに送らず、預からない。音声・動画データは受け付けない。
- エラー報告にも会話本文を含めない。
- 保存はブラウザ内または本人によるダウンロードを基本とし、削除できるようにする。
- モデルの取得やサイトの配信に伴う通信と、会話データの外部送信を明確に区別する。
- データの保管・復旧を運営側が引き受けない方針を説明する。
- 端末内処理だけで責任が全面的になくなるとは保証しない。
- 改良提案を採用する際にも、会話を外部送信しない原則を確認する。
- ブラウザ保存は消去・容量制限の影響を受ける。第16章に定める明示的保存と持ち出し用JSON、復元確認を提供し、永続性を保証しない。

## 13. ダウンロード・他のAIへの受け渡し

- 閲覧だけでなく、自分のAIに渡せる会話資料をダウンロードできる。
- 原文、人物、問い・回答、分岐、立場の変化、合意、未回答、根拠との対応を含める。
- 事実と推定の区別、出典、対象範囲を維持する。
- 全体または特定論点を選べる。一部出力では省略があることを示す。
- 人物ラベルの仮名化と出力プレビューを提供する。本文や引用、URL等からの完全な匿名化・再識別防止は保証せず、残る識別情報を利用者が確認する。
- 別AIで追加質問しても、根拠の発言へ戻れる構成にする。
- 持ち出し先での偏ったプロンプトや悪用は完全には防げない。元記録と反対根拠を確認できる環境を重視する。

## 14. オープンソースの公開物

- プログラム本体。
- AIへの指示文、分析・判断基準。
- データ構造、保存・出力形式。
- 使用モデルの版、取得元、取得方法、利用・再配布条件。
- 起動、開発、テストの手順。
- 公開可能な架空または許可済みサンプル会話と期待する分析例。
- 実装済み、計画中、既知の制約の区別。
- 改善提案やフォークからの変更を確認するための案内。

モデル本体の大きなファイルをすべてリポジトリに同梱する必要はない。配布元・取得方式・容量・通信量・ライセンスの検討が必要。

何ができるか、操作手順、画面例、初回準備、保存・削除、対応環境、分析の限界、困った場合の対処。

## 16. 設計判断・未検証事項・採用ゲート

### 16.1 初期版の範囲と入力契約

初期公開版（v0.1アプリ）の必須範囲は、テキスト読み込みから根拠付き分岐図、原文一覧、最終まとめ、訂正、端末内保存、エクスポート／復元までの一連の操作とする。「自動分析の品質が合格すること」と「原文を失わず手動で確認・修正できること」を別々に検証する。

| 入力 | 方針・制約 | 導入段階 |
| --- | --- | --- |
| 貼り付け、`.txt`、`.md` | UTF-8（BOM可）。Markdownはテキストとして読み、HTML・スクリプト・画像を実行／表示しない | P1 |
| `.srt`、`.vtt` | 文字起こし済み字幕テキストのみ。時刻は出典の補助情報。音声との照合はしない | P1 |
| `.docx` | 本文の段落・表の文字を安全に抽出し、段落番号等へ対応付ける。脚注等の対応範囲を表示する | P4 |
| `.pdf` | 埋め込みテキストのある文書のみ。ページと抽出順を保持し、読み順を確認できる | P4 |

- 1プロジェクトは同一会話の連続記録を基本とし、最大10ファイル、合計30 MiB、抽出後合計50,000 Unicodeコードポイント、最大5,000発言とする。資料テキストも文字数上限に含む。これらは防御上限であり、処理時間の保証ではない。
- `.txt`／`.md`／`.srt`／`.vtt` は1ファイル2 MiB、`.docx`／`.pdf` は1ファイル20 MiB、PDFは200ページまで。複数記録の順序と人物の対応は読み込み時に確認可能にする。時刻のリセットだけで別ファイルの順序を推測しない。
- 上限超過は解析前または抽出中に止め、何が何件・どの上限を超えたかを示す。先頭だけを無断で分析して全件完了と見せない。複数回の分割プロジェクトを提案し、将来の上限緩和は計測後に行う。
- Shift_JIS等の文字コード自動推測、旧`.doc`、`.docm`、HTML、画像、圧縮アーカイブ単体、暗号化・パスワード付き文書、URL経由取得、音声・動画は初期版で受け付けない。UTF-8へ変換する等の対処を示す。
- 拡張子・MIMEだけを信頼せずファイルの構造も検査する。空、破損、文字なしPDF、読み順が不明な段組み、未対応注釈・図表・埋め込みオブジェクトは警告する。抽出結果の確認後に解析する。抽出されなかった内容を推測で補わない。
- DOCXはZIP展開の合計50 MiB、単一エントリ10 MiB、最大2,000エントリを上限とし、展開中にも検査する。パストラバーサル、過大展開、外部参照、DTD／外部実体を拒否する。外部画像やリンク先は取得しない。
- PDF.jsとMammothは抽出の候補とする。PDF.jsはローカルバイト列を入力する。Mammothは原文HTMLを安全化するライブラリではないため、未信頼HTMLの直接挿入を禁止し、外部ファイルアクセスを無効のままにする。候補選定時に固定版で再確認する。[PDF.js API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html)、[Mammothのセキュリティ説明](https://github.com/mwilliamson/mammoth.js#security)
- パーサーは専用Workerで実行し、30秒／ファイルのタイムアウトと中止を設ける。抽出失敗は当該ファイル単位で扱い、すでに確認済みの他ファイルを失わせない。制限が適用できないパーサーは採用しない。

### 16.2 構成とモデル選定

静的Webアプリを基本とし、TypeScript、React、Viteを初期候補とする。推論・パースをWorkerに分離し、データ検証・保存・図表示を分ける。テストは単体／結合と実ブラウザE2Eを用意する。個々のパッケージ版はP0で公式配布元・ライセンス・脆弱性を確認して固定し、依存ロックファイルを管理する。現時点では依存追加も行っていない。

- 第一候補はWebLLM＋WebGPU。公式の対応モデル一覧から、モバイルでの成立性を調べる小型候補を含め、日本語の構造抽出に適した量子化済みテキストモデルを最大3候補選び、同じ評価セットで比較する。モデル名・重み・トークナイザー・量子化方式・ランタイム版・設定・プロンプトを一組として固定する。WebLLMにはモデル取得とWorker実行の仕組みがあるが、本ツールでの動作は未検証。[基本利用](https://webllm.mlc.ai/docs/user/basic_usage.html)、[Worker実行](https://webllm.mlc.ai/docs/user/advanced_usage.html#using-workers)
- 比較候補はTransformers.js＋ONNX Runtime Web。WASMとWebGPUの選択肢はあるが、モデル・演算・メモリ条件により動作が異なるため、CPU上で同等に動くとは約束しない。[Transformers.js公式文書](https://huggingface.co/docs/transformers.js/index)、[ONNX Runtime Web公式文書](https://onnxruntime.ai/docs/tutorials/web/)
- 検証対象は、16 GiBメモリ以上のApple Silicon MacとWindows PC各1台以上、リリース時のデスクトップChrome／Edgeの安定版および前のメジャー版。機種・OS・GPU・ブラウザの正確な版を評価報告に残す。MacではChrome、WindowsではChromeとEdgeを試す。WebGPUの機能検査・試験推論に成功した組合せだけを対応環境とする。
- モバイル成立性の検証対象に、現行iPhoneのSafari（iPhone 17 Pro等の実機）を加える。デスクトップを基準検証環境とし、モバイル・他ブラウザ・タブレットのAI対応は、機能検査と品質・速度・メモリの実測で公開範囲を決定する。端末名だけでAI動作を保証しない。未検証はその旨を示し、GPU未対応または品質・性能未達の場合は原文閲覧・手動修正・既存結果の復元／出力に限定する。これらの基本操作も実機で確認してから対応と表示する。
- 初回取得の目標上限はモデル関連ファイル合計2.5 GiB、デスクトップ検証環境の推論時追加メモリの目標上限は6 GiB。モバイルはOSやブラウザの一律上限を推定して保証せず、P0で実機の失敗・復旧挙動と余裕を測り、端末／OS／モデル別の安全上限を設定してG4に別掲する。小型モデルにも同じ品質ゲートを適用する。実際の取得量・必要空き容量・見込み時間を開始前に表示する。小さいモデルを選ぶだけで品質が確保されるとは扱わない。
- 採用は16.8の品質・性能・安全ゲートと利用／再配布条件をすべて満たす場合に限る。第一候補が不合格なら比較候補を同じ条件で試す。どちらも不合格ならAI公開を保留し、手動整理を含む試作の結果と不足を示して計画を再レビューする。有料API、遠隔推論、別サービスへの送信に自動で切り替えない。
- 将来の推論差し替えに備え、UIはランタイム固有APIを直接呼ばない。文書から返る指示をツール実行・ネットワークアクセス・設定変更として解釈しない。

### 16.3 原文・根拠・訂正のデータ契約

保存形式は版付きJSONを正本にし、型とJSON Schemaを公開する。最低限、次の区分を持つ。

| 区分 | 必須内容 |
| --- | --- |
| Project | projectId、schemaVersion、作成／更新時刻、入力順、処理範囲、解析状態 |
| Source | sourceId、sourceVersionId、表示名、形式、元ファイルSHA-256、抽出方式／版、抽出原文、位置対応、警告 |
| Utterance | utteranceId、sourceVersionId、順序、原文範囲、話者候補、任意の入力時刻、引用・不明表示 |
| Question / Claim | 固有ID、種類、対象・条件・用語、親問、根拠範囲、作成者区分、保留理由 |
| Relation | 固有ID、始点／終点、応答・支持・反対・派生・別問い・復帰・合流等の種別、根拠範囲 |
| Assessment | 回答状況、合意状況、解決状況、外部確認状況を独立した値で保持 |
| AnalysisRun | runId、入力版、モデル／ランタイム／指示文の版とハッシュ、設定、チャンク状態、対象範囲、失敗 |
| Revision | revisionId、対象ID、変更前後、理由、変更者区分、時刻、参照元の版 |

- sourceId等の同一性は作成時のUUIDで固定する。再解析・並べ替え・名称変更で変えない。同一バイトの再入力はハッシュで通知するが、別の記録を自動で同一人物・同一発言へ統合しない。
- 原入力・抽出原文は不変とする。原文訂正は新しいsourceVersionIdとして追加し、旧版を残す。モデル向けの空白等の正規化は別テキストと対応表を持ち、引用を正規化結果で置き換えない。
- evidenceRefはsourceVersionId、utteranceId、抽出原文内の開始・終了オフセット（UTF-16コード単位・半開区間）、引用文字列、任意のページ／段落番号で表現する。件数上限の「文字数」はコードポイントであり、オフセットの単位と混同しない。絵文字・結合文字・改行を含む往復テストを必須とする。
- Evidenceの参照先と引用文字列が完全一致することをコードで検査する。根拠がない生成項目や存在しないIDは図へ採用せず、検証エラーにする。引用一致は解釈の正しさを保証しないため、意味評価を別途行う。
- 全発言に「分析結果へ対応済み／相槌等として折り畳み／未整理／解析失敗」のいずれかを付け、反映先を逆引きできる。折り畳みや未整理を削除扱いにしない。
- 訂正・撤回・異議は追記履歴とし、AI出力と人の変更を分ける。ローカルアプリには本人認証機能がないため、「本人確認済み」は自動付与せず、「利用者が本人説明として登録・身元未検証」等の出所を示す。第三者の異議も記録した人と対象を残す。
- 再解析は新しいrunIdに保存し、利用者の訂正を無断で上書きしない。旧解析・新解析・訂正の衝突を比較し、採用・保留を選べるようにする。変更履歴は編集経緯であり、電子署名や改ざん不能の証明ではない。

### 16.4 分割解析と全体文脈の照合

1. 文書境界・発言境界を保持して入力を分割する。初期目安は1チャンク2,000トークン、前後の重なり200トークン。採用モデルのトークナイザーで数え、入力・指示・出力予約の合計が実際のコンテキスト長を超えないよう調整する。
2. 長い1発言は複数spanに分け、元のutteranceIdを維持する。境界で切れた否定・条件・引用は隣接spanを併読する。チャンク化された原文を短い要約で置換しない。
3. チャンク内で問い・回答・主張・根拠を抽出し、構造検証を行う。同じ根拠範囲の重複候補は統合候補として記録する。
4. 人物、用語、問い、未回答の索引を作り、離れたチャンク間の継続・復帰・立場変化を照合する。照合時も関連する元発言を参照する。表現が似ているだけで人物や問いを自動統合しない。
5. 全体を統合し、孤立ノード、参照切れ、重複、時系列の矛盾、未反映発言を検査する。統合に確信が持てない場合は複数候補または保留を残す。
6. 最終まとめは検証済みの構造と原文参照から作る。元発言が見えない圧縮要約だけを繰り返して結論を生成しない。未処理チャンクがある結果には対象範囲と「部分結果」を常に表示する。

数値的な「確信度」を正確さの確率として表示しない。初期版では「根拠明示／複数解釈／判断保留」と理由を使う。人物・条件・否定・引用者の取り違えや遠距離参照は16.8の長文テストで評価する。

### 16.5 判定基準と外部情報の境界

- 問いの継続／派生：対象と解くべき判断を共有し、前提・理由・条件の検討として元の問いに戻る関係を根拠付きで示せるもの。別の問い：判断対象または求められる結論が変わるもの。不足時は「関係未確定」とする。
- 回答：問いの要求対象に応じる発言があるか。理由だけ・部分的対応は区別し、回答の存在から正しさ・合意・解決を推論しない。
- 合意：参加者と合意対象・条件が明示的に対応するもの。沈黙、相槌、多数決、論争の終了だけで全員合意を推論しない。
- 立場：賛成／反対／明示的中立／判断保留／条件付き／表明なし／二択前提への異議を分ける。言葉だけの極性ではなく対象・時点・条件を保存する。
- 解決状況：未解決／条件付きの到達点／当事者が解決と表明等を区別し、その発言を添える。アプリが真理を確定したような「解決」バッジを付けない。
- 外部確認：未確認／利用者提供資料に支持候補あり／反証候補あり／資料間で不一致／利用者の確認記録ありを区別する。確認者区分、出典、対象時点、アクセス日、確認対象、限界を保持する。リンクだけでは本文を読んだ扱いにしない。
- 初期版は検索エンジン、自動URL取得、外部AI、ファクトチェックAPIを使わない。利用者が資料本文を追加したときだけ端末内で対照する。モデルの既存知識は外部裏づけに数えない。
- 出典URLは自動アクセス・プレビュー・プリフェッチしない。利用者が開く操作を選んだ場合だけ別タブに移動し、サイトを離れる旨を示す。URLはhttp/httpsに限定し、認証情報や本文を自動付加せず、referrerを送らない設定を使う。機密情報が入ったURLの共有前確認も促す。

### 16.6 プライバシー、安全性、保存・復元

- 会話本文、名前、入力ファイル名、ハッシュ、分析結果をネットワーク、アクセス解析、エラーレポート、URLクエリへ送らない。外部フォント、広告、追跡タグ、解析SDK、外部埋め込みを使わない。依存スクリプトはビルドに固定して含め、実行時の任意CDN読み込みを禁止する。
- 通信をサイト静的資産と、利用者が明示的に開始するモデル取得に限定する。取得先・容量・ライセンスを事前表示し、モデル取得には配布元からIPアドレス等が見えることを説明する。初回取得と更新が完了する前の完全オフライン利用は保証しない。
- モデル・WASM等は固定版・許可された取得先から読み、可能な資産はハッシュ検証する。キャッシュが破損したら当該資産の再取得を案内し、会話データは送らない。キャッシュ済み利用のオフライン動作をP6で検証する。
- 全入力、モデル出力、インポートJSONを未信頼データとして検証する。本文はテキストとして描画する。XSS、危険URL、Prototype Pollution、過大オブジェクト、循環／参照切れ、入力内のプロンプトインジェクションを試験する。モデルにはファイル、ネットワーク、コード実行のツールを与えない。
- CSPを配信環境で実際に有効にできる範囲で設定する。WebGPU／WASMに必要な例外は最小限とし、GitHub Pagesのヘッダー制約を含めてP0で確認する。必要な安全要件を満たさない場合は配信構成を再検討し、緩い設定へ黙って変更しない。
- 既定は一時作業とし、「この端末に保存」を選んだプロジェクトのみIndexedDBへ保存する。保存選択後は版付きスナップショットと変更履歴をトランザクションで自動保存し、保存時刻・未保存状態を表示する。「最近の作業」は保存済みのみ表示する。
- 初期版の保存データはアプリ独自の暗号化を行わない。共有端末やブラウザプロファイルにアクセスできる人から読まれる可能性、端末内処理がアクセス制御の代わりにはならないことを説明する。
- ブラウザ保存は消去・容量不足・追い出しの可能性がある。容量を確認し、保存失敗時は成功表示をせず、作業中データを保持してダウンロードを案内する。永続保存のブラウザ要求を使う場合は利用者操作で行う。[保存容量と消去の制約](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- エクスポートはUTF-8の完全復元用`.rontenseiri.json`、読み物・他AI用`.md`、図の静的`.svg`を用意する。図には原文対応・生成版・推定表示を付け、SVG内へ実行コードや外部参照を入れない。Markdown／SVGだけでは完全復元できないと明示する。
- JSONは原文、人物、根拠ID、解析、訂正履歴、スキーマ版、処理範囲を含める。元のPDF／DOCXバイナリとモデルは初期の保存・エクスポートに含めず、文書レイアウトや元ファイル復元はできないと示す。元ファイルの保管を案内する。
- 保存・履歴追記前に完全JSONのサイズを検査する。50 MiBを超える操作は拒否し、既存データのエクスポートと別プロジェクトへの引継ぎを案内する。履歴を無断で間引かず、書き出した完全JSONが自分の復元上限内であることを検査する。上限超過を起こす編集中の内容も破棄せず「未保存」と表示し、最後の保存済み完全JSONに加え、編集中内容の全文を別テキストとしてダウンロードできるようにする。後者だけではプロジェクト全体を復元できないことを示す。
- インポートは最大50 MiB、16.1の文字・発言上限、参照整合性、スキーマ版を検査し、既存プロジェクトを上書きせず別コピーとして取り込む。未知の新しい版は拒否して対処を示す。マイグレーション前の版は保存し、元データを失わせない。
- 論点限定出力には選択範囲、省略の事実、関連する反対根拠・未解決点を含める。範囲外の人物名・ファイル名・出典URL・履歴が漏れないか検査する。仮名化時の対応表は既定で出力しない。出力プレビューを必須にし、完全匿名化とは表示しない。
- ダウンロード後の他AIへの送信は利用者自身が行う。本ツールから外部AIへ送る機能は実装しない。ファイルには機密情報・個人情報を含み得る旨を示す。
- 保存済みプロジェクトの削除は対象・影響を示して確認し、先にJSON控えを作れる導線を置く。会話データとモデルキャッシュは別々に選べるようにする。端末・ダウンロード済みコピーの完全消去までは保証しない。

### 16.7 画面、アクセシビリティ、失敗・取消・復旧

- 初期結果は分岐図。元の大きい問いを固定表示し、図⇄一覧⇄原文の選択状態を同期する。階層の折り畳み、検索、問いの切替、関連枝のみ表示を用意する。全体にノードが多くても一度に描画する数を制御する。
- 図と同じ情報に到達できるキーボード操作可能な一覧を常設する。色に加えて人物ラベル・線種・記録／推定／訂正の文字表示を使い、読み上げ、フォーカス順、拡大表示、コントラスト、動きを減らす設定を検証する。WCAG 2.2 AAを目標にし、適合を検証前に表明しない。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- 状態機械は「未開始→入力検査→抽出確認→モデル準備→チャンク解析→全体照合→結果」の正常系と、「取消／失敗／部分結果」を持つ。実行中は現在段階、完了件数、残作業、経過時間を示す。生成前に正確な所要時間を約束しない。
- 取消は3秒以内にUIが応答する目標とし、可能なら推論を停止、停止できないWorkerは終了する。runIdで遅れて返った旧結果を捨てる。新しい実行が古い実行の出力で上書きされないようにする。
- 構造不正なモデル出力は同一チャンクにつき最大1回だけ修復再試行し、それでも失敗なら明示する。ネットワーク／モデル準備の再試行は入力を送らず対象資産だけに限定する。無限再試行をしない。
- タブ終了、リロード、メモリ不足、GPU喪失、モデル取得中断、ストレージ不足を区別する。保存済みなら最後のコミット済みチャンクから再開し、一時作業なら閉じると失われる可能性を事前表示する。復旧時にモデル／指示文が変わっていれば新しいrunIdを作る。
- 本人の訂正を取り消す操作は履歴を残す。再解析、インポート、別タブでの同時編集、戻る／進む、連打を試験し、複数タブは書込みロックまたは読取り専用で競合を防ぐ。

### 16.8 日本語評価とリリースの受入ゲート

以下はすべて**提案する合格基準**。本計画作成時点で測定しておらず、達成を主張しない。品質は単一の平均スコアに集約せず、例数、失敗例、分野別結果も公開する。

**評価資料と方法**

- 架空または公開許諾済みの日本語会話60件以上を用意し、40件を開発用、20件を未使用の固定評価用とする。同じ会話の言い換えや断片を両側に混ぜない。
- 二人の評価者が独立して問い・根拠・対応関係・重要発言を付け、不一致を記録して調整する。複数の妥当な読みは正解集合として残し、無理に単一正解にしない。評価者間一致も報告する。
- 否定、二重否定、条件付き賛否、保留、理由のみ、相槌、引用、皮肉、曖昧な主語、複数質問、用語の変更、訂正・撤回、質問側の前提変更、遠く離れた問いへの復帰、切り抜き不足、表記ゆれ、話者不明を含める。会議・記者会見・日常会話等の偏りも記録する。
- 20件の固定評価に加え、50,000文字近く・5,000発言近く・500ノード以上の長文／大規模合成ケースを5件以上、未知・曖昧・悪意ある入力の安全ケースを20件以上用意する。重要ラベルは各20例以上を含め、不足時は追加する。
- チャンク統合あり／なしの比較、同じ入力で3回の反復を行い、不安定さ・取りこぼし・分岐統合誤りを測る。モデル・指示文の調整に固定評価を繰り返し使い始めたら、別の未使用評価セットで再検証する。

性能測定は入力長、発言数、ノード数、キャッシュ状態、モデル、出力長、OS／ブラウザ／GPU、計測方法を記録する。メモリ計測は利用可能なOS／ブラウザの計測器を用い、GPUメモリが別計測なら明記する。測れない指標は未測定としてゲートを未完了にする。小さな固定セットで誤り0件でも、実利用で誤りがないとは主張しない。

### 17.1 責務別の構成案と共通インターフェース

| 位置 | 責務 |
| --- | --- |

共通契約は次を出発点とし、P1で型を確定する。

- `parseSource(file, limits, signal) -> ParsedSource`：抽出原文、位置対応、メタデータ、警告を返す。失敗時は理由付きエラーで、成功のふりをした空文字を返さない。
- `validateEvidence(project, evidenceRef) -> ValidationResult`：版、ID、範囲、引用一致を検査する。推論結果の採用前と復元時に共通利用する。
- `analyzeProject(projectSnapshot, modelConfig, signal) -> AsyncIterable<AnalysisEvent>`：runIdごとの進捗・検証済みチャンク・失敗・最終結果を返す。入力スナップショットは変更しない。
- `applyRevision(project, revision) -> ProjectSnapshot`：変更前後と理由を追加し、新しいスナップショットを返す。原文・旧解析を破壊しない。
- `saveSnapshot(snapshot) -> SaveResult`、`exportProject(snapshot, scope, format) -> Blob`、`importProject(bytes) -> ImportResult`：保存失敗、部分出力、互換性、別コピーとしての復元を明示する。
