# R17: 登録済みの主張・条件・例外の内容と根拠を訂正する

## 今回できるようにすること

v0.4計画R17・P3/P5に沿い、「問い・根拠」に登録済みの意味項目を通常UIで修正できるようにする。これまでは登録しかできず、内容や根拠が誤っていても同じIDのまま直せなかった。テスト組合せの追加ではなく、新しい編集操作とドメインコマンドを追加する独立した機能sliceである。

#57の公開head `522916d6b5b29009ff5ca67a4c2e7fac710a4c5a` を親として積む。#57本来のリンク追加機能を変更せず、関連する単体・通常UI・保存・出力・Undo・本書を一つの機能PRにまとめる。外部AI、外部サービス、追加パッケージを使わず、ローカルファーストを維持する。

公開前の12:49 JSTのno-cache再確認では#55/#56/#57はstack内でマージ済みに変化していたが、mainは `b0de54d1510832189cc7840749cfc66b50bdc4e6` のままだった。#57のbranch参照は上記の確定headに存在するため、このbranchをbaseにして機能差分を保つ。stack内のPRマージ状態をmain統合と同一視せず、rebase・merge・branchの書換えはしない。

## 編集できるもの、保持するもの

既存カードの「意味項目 … を修正」から、内容、項目種別、明示的な発言根拠、登録済みEvidenceとの関連を変更し、理由を付けて保存する。新規登録フォームを再利用するが、編集モード、フォーカス移動、キャンセルを区別する。修正失敗時は下書きを保持し、画面移動の既存draftガードも働く。

`updateSemanticItem` は実行時にも編集可能な4フィールドだけを採用する。ID、actor、登録時点と対象時点、確度、scope、termDefinition、counterargumentToId等は保持する。原文、既存の問い版、旧版への応答、他の意味項目、Evidence自体を書き換えない。関連を外してもEvidenceは削除せず、反証や裏付けが「存在しない」と断定しない。確度は編集時には読取り専用とし、訂正しただけで確認済み・外部検証済みへ昇格させない。変更した人の操作は理由付き共有履歴に残すが、既存actorを本人認証や新しい原発言の出所に読み替えない。

原文のない空の発言根拠、無効・重複参照、空白だけの内容や理由、不正な種別、confirmedなのにEvidenceがない状態は拒否し、失敗しても入力Projectは不変とする。任意メモ、削除、意味項目の分割・統合、確度・時点の変更は今回追加しない。

排他的A/B解釈が管理する前提・結論は汎用エディタから変更できない。カードに専用編集への案内を出し、API側でも拒否する。候補の片側だけを変更して既存の原子的な管理契約を迂回しない。専用候補から参照される通常の既存結論まで、一律に所有物とは扱わない。

## 訂正による再確認とUndo

同じIDを保ち、`reasoning:semantic-item-updated` を共有Undoの1単位として記録する。変更前後の意味状態はProject履歴に、reasoningの監査イベントはrevision IDへの参照だけを保存する。Undoは内容・根拠・要約の確認状態とactive graphを戻し、変更履歴を削除しない。

旧・新の発言根拠の和集合を既存の明示依存伝播へ渡す。さらに変更した意味項目IDを起点に、発言を共有しなくても明示的にその項目へ反論する応答、解釈、uncertaintyの関連を追う。その後、既存の発言依存の固定点処理へ接続する。要約は明示依存に基づいて要再確認とし、自動で新しい結論を書かない。意味項目ID起点の反論追跡は今回の訂正コマンドで起動し、既存の原文・問い・応答の編集経路を別機能として一括変更しない。

サポのexact-head `9af9295ec3b4efb3e6b8fc41710107e4f929ef9f` 静的レビューで、意味項目I1→発言依存→中間項目I2→I2への反論→要約という順序では、発言固定点へ移ったときに意味項目起点の追跡モードが失われるP2が見つかった。新しい回帰で下流Cの `needsReview: false` を再現し、生ログを保持した。修正は同じ意味項目起点を発言固定点の各反復へ引き継ぐものに限定する。既存の原文・問い・応答訂正は空の起点を既定値とし、今回の修正で追跡モードを広げない。回帰は直接反論や共有Evidenceによる別経路を取り除き、この交互連鎖だけで下流の要再確認、独立成分不変、完全JSON往復と共有Undoを確認する。

依存は現在の発言/Evidence/関係IDベースであり、同じ発言に複数の意味項目がある場合は保守的に再確認範囲が広がり得る。テキスト類似度や意味推定で無関係と判断しない。任意の再解析、精密な意味依存モデル、要約の自動再計算は未実装である。

## まとめて検証すること

固定fixtureではSが原文を所有する一方で要約依存は空、Aは旧発言U02だけ、Nは新発言U03だけ、Cは下流U04だけを要約依存に持つ。A/N/Cの所有発言は依存先から分離し、Bは独立した発言・項目・根拠・要約を持つ。旧版を対象にする既存応答がI1を反論先として参照する。

準備時には通常の話者訂正でAが要再確認になった状態を保持する。サポの提案どおり、画面ではA/N/C/Bを「まとめを編集」→理由入力→「確認した整理内容を保存」で確認し、保存済みの全議題cleanを明示assertしてから対象操作を行う。fixtureで要再確認を直接解除しない。単体は同じ正規確認コマンドを使う。

単体では4フィールドの修正、旧・新・下流の失効、内容だけの変更でも反論先参照が失効すること、独立成分全object不変、出所/ID/時点/確度の保持、runtime patch注入、不正入力、排他的解釈の保護、共有Undo、完全JSON往復と限定出力の非漏洩をまとめて検査する。

通常UIでは1440pxと390pxで、確認済み基準状態→明示修正→autosave→native readonly IndexedDB観測→最近の作業から再開→カード/図/振り返り/完全JSON→Undo→保存→再開を検査する。別ケースで検証エラー・下書きガード・キャンセルと、排他的解釈の保護を検査する。fixtureはNode側で作り、通常JSON復元を使う。ブラウザ側の内部モジュールimport・状態注入・保存書き込みは使わない。外部通信を遮断・記録する。

## 証拠と残る範囲

最終headのSHA、差分、実行前後のworktree、単体/ブラウザJSON、format/buildの生ログと終了コードを一意の証跡ディレクトリへ保存し、PR本文へ正確な結果を記録する。未実装時の失敗、途中失敗・中断を後の成功で上書きしない。ローカル結果とCI結果、実装と独立レビュー、Draft公開とmain統合を区別する。

図や発言一覧へ意味項目エッジを新設するものではなく、カードの内容・原文参照と既存の共通再確認状態を扱う。R17全操作、R15/P3/P5全体、意味品質、実機、性能、保存競合、G0–G8受入は完了扱いにしない。中央の受入ステータスは更新しない。マージ・ready・rebase・force-pushは行わない。
