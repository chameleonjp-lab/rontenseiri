# v0.4の残項目を齟齬なく実行するための手順書

この手順書は、既存機能を作り直す指示ではない。**最新の版で現状と証拠を確かめ、不足だけを実装し、同じ最終版で個別要件と品質ゲートを受け入れる**ための実行契約である。文書PRの採用だけで、実装・測定・モデル採用・実機確保・公開を承認したことにはしない。

根拠は[統合要件・開発計画 v0.4](../requirements-and-development-plan.md)第1–20章、[全件レビュー](../reviews/requirements-gap-review-2026-10-17.md)、[要件台帳](../evaluation/requirements-status.md)、[評価ルーブリック](../../evals/rubric.md)。計画の要件とゲートを緩和・置換しない。会話内の過去の一覧は、ここで公式計画に対応付けた内容で実行する。未承認の判断は未承認と残す。

## まず押さえる完成境界

- **文書PR完了**：本書と参照導線がレビュー可能なDraftになり、文書だけの差分、版・対応表・リンクの検査結果が示されること。アプリ実装を含めない。
- **設計検証版で停止**：AI disabled、実測・実機・権利等の未確認を表示したまま、所有者が明示して停止する選択。これは可能だが、**v0.4全体の完成ではない**。停止時にも未達・保存データの取扱い・再開条件を残す。一般公開の承認を含まない。
- **公開承認前の候補・準備審査（S09）**：G0–G6・G8の技術証拠とG7の権利・安全・文書証拠を揃え、所有者へ公開可否を審査する材料を渡す段階。G7の最終公開承認は明示的に保留し、G0–G8全受入・v0.4完成とは呼ばない。
- **v0.4要件受入完了**：R01–R33とG0–G8の全必要証拠を、一つの最終候補SHA・固定構成・対応環境に紐付け、未達・未測定を隠さず所有者が受け入れること。G7は所有者の別途の公開承認を記録して初めて合格にできる。別版の部分成功を足し合わせない。
- **公開完了**：上記に加え、権利・公開物・配信先・更新／巻戻し手順の別承認、承認後の配備、実URLのスモーク検査まで揃うこと。PR作成・マージ・タグ・配備・公開済み報告はそれぞれ別の状態。

PDF/DOCX等を計画に従うレビューで対応範囲から外す場合は、理由・影響・代替・再評価条件を計画へ正式に反映する。文書に書かずに対象外へ移し、元のv0.4全件完了と称することはできない。音声・動画・録音・再生・取得・文字起こし・声による話者識別・OCR・URL取得・外部検索・運営側有料AI API・外部AI自動送信は引き続き対象外。

## 2. 作業を混ぜないための共通カード

すべての作業を下の種類で記録する。Vで既に満たすと分かった場合、Iを作業実績として水増しせず「実装不要・理由・証拠」とする。

## 4. 原文・入力・パーサーの実行契約（S02・P1/P4）

### 4.1 上限は単位とタイミングまで固定する

次は公式計画§16.1/16.6の防御上限であり快適性の保証ではない。各値で`下限／上限ちょうど／上限+1`、複数ファイル合算、抽出中超過、キャンセル、保存／復元の同一計数を試験する。

| 対象                             | 上限／受入条件                                                                                | 必須失敗証拠                                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 現行プロジェクト入力             | 10ファイル、合計30 MiB、抽出後50,000 Unicodeコードポイント、5,000発言。参考資料も文字数へ算入 | 11ファイル／合算超過／50,001コードポイント／5,001発言は理由付き停止。先頭だけで全件完了にしない       |
| TXT/MD/SRT/VTT                   | 1ファイル2 MiB、UTF-8（BOM可）、貼付も同等の現行入力制限                                      | 不正UTF-8、未知形式、空、破損、改行・絵文字・結合文字。MDのHTML/script/画像を実行・取得しない         |
| PDF/DOCX（正式対応を目指す場合） | 1ファイル20 MiB、PDF200ページ。PDFは埋込文字のみ                                              | 201ページ、文字なし、暗号化、破損、段組み読み順、非対応注釈／図表を確認。失われた範囲を推測補完しない |
| DOCX ZIP内部                     | 展開合計50 MiB、単一entry10 MiB、2,000 entries。展開前・展開中に検査                          | zip bomb、path traversal、外部参照、DTD/外部実体拒否。リンクや外部画像へ接続しない                    |
| パーサー資源                     | 専用Worker、30秒／ファイルtimeout、明示取消                                                   | 主スレッドを止める／制限不能なら採用不可。失敗ファイルだけ除外し確認済み他ファイルを残す              |

1 MiBは1,048,576 bytes。容量の実装単位をVで照合し、表示と検査を一致させる。入力の文字数はコードポイント、根拠オフセットはUTF-16であり同じ単位ではない。旧版を現行入力50,000文字へ合算して、同じ長さの訂正を誤拒否しない。全量は50 MiBで防御し、保存できた完全JSONが自分のimport上限内であることを確認する。

### 4.2 対応形式と抽出確認

Vでは`src/input/parse.ts`、`documents.ts`、`docx.ts`、通常入力UIの結線を別々に確認する。固定mainでREADMEはPDF通常UIをfail closed、DOCX/PDFを実験APIと説明している。コードの存在から対応と称さず、また古いREADMEだけで新しい経路の不存在を断定しない。

Iが必要なら、拡張子/MIMEに加え構造を検査し、Worker隔離・資源制限・ローカルbytes入力を先に通してからUIへ結ぶ。PDF.js/Mammoth等は候補に過ぎず、固定版で安全条件・ライセンスを再確認する。MammothのHTMLをそのまま挿入しない。外部file accessは無効。拒否対象はShift_JIS自動推定、旧doc/docm、HTML、画像、単体アーカイブ、暗号化文書、URL、音声・動画。UTF-8変換等の対処を案内し、音声認識やOCRを追加しない。

### 4.3 R02–R05の固定失敗例

- `extent=全文/抜粋/不明`と利用者の欠落申告を入力時に保持する。抜粋の末尾を会話の終わりにせず、未回答や合意は「提供記録内」の判定。図・まとめ・出力・復元に同じ範囲を残す。
- `SourceRole=会話本文/参考資料/後日説明`を分ける。資料を足しても当時の参加者・発言順・合意を自動で変えない。役割変更は履歴へ。
- 抽出全文の全範囲を発言／非発言／理由付き対象外／未確定へ分類する。全発言の状態付与率だけで合格にしない。話者ラベルなし段落・短い訂正をわざと発言化前に落とすと検査が失敗することを確認。
- SRTとVTTを別契約にする。VTTの合法な重複・同一時刻を拒否せず、不正終了時刻を別検出。字幕cueと発言は1対1としない。複数cueの一発言、一cueの複数話者、境界をまたぐ否定、反復表示と実際の繰返しを原文参照付きで保持する。入力時刻を実メディアと照合済みにしない。

### 4.4 ID・原文不変・根拠参照

`Project/Source/Utterance/Question/Claim/Relation/Assessment/AnalysisRun/Revision`の版付き契約とJSON SchemaをVで照合する。計画中の候補パスを現存と取り違えず、新設が必要ならカードへ明記する。

1. 作成時UUIDの同一性を維持。再解析・並替・改名でIDを変えない。同一bytes hashは重複通知に使い、人物・別発言の自動統合には使わない。
2. 原入力・抽出原文を不変にし、訂正は新sourceVersionId、旧版は保持。モデル用正規化は別テキスト＋原文対応表。元の引用を正規化文で置換しない。
3. `evidenceRef={sourceVersionId,utteranceId,start,end,quote,...}`のstart/endは**UTF-16コード単位・半開区間**。版／ID／境界／完全引用一致を採用前と復元時の共通検証で確かめる。
4. 絵文字・結合文字・CRLF/LF、同一原文内の増減訂正と後続offset rebasing、分割span／重複引用、旧版参照を往復する。存在しないID、範囲外、引用不一致、根拠のないAI生成項目は採用拒否。引用一致だけで解釈が正しいとは数えない。
5. 全発言に対応済み／相槌等の折畳み／未整理／解析失敗を付け、原文→発言→構造／まとめ、構造→根拠を逆引きできる。相槌を削除したり「はい」を自動合意にしない。
6. 本人認証はない。「本人確認済み」を自動付与せず、利用者が本人説明として登録・身元未検証という出所を残す。履歴は編集経緯で、署名・改ざん不能証明ではない。

Eは原文hash／抽出方式版／全span coverage／不一致検出ログ／往復比較／通常UI導線を含める。G1の100%は複数指標それぞれで判定する。

## 9. 固定評価・人手採点・公平性・利用者成果（S07・P0/P2/P6）

### 9.1 データを確保して凍結する

Qは架空または許諾済み日本語会話60件以上を確保し、40開発／20未使用固定評価に分ける。同じ会話の断片・言換え・公平性ペアを両側へ漏らさない。会議・会見・日常等の偏りと権利を記録。追加で50,000文字近く／5,000発言近く／500node以上の大規模合成5件以上、安全20件以上、重要ラベル各20例以上を揃える。不足なら追加する。

現`evals/cases.json`の架空21件は開発fixtureで、60件・二人の独立注釈・固定未使用20件・実予測を代替しない。`npm run evaluate`のempty結果はnot-run。goldをpredictionへコピーしたselftestも実モデル評価でない。

各caseにID、版、hash、会話family、役割／記録範囲、原文・根拠span、期待集合、重要発言、許容解釈、失敗分類、権利根拠を付ける。固定評価をprompt調整に繰返し使い始めたら、汚染記録を残し別の未使用setで再検証する。単に同じ文章の言換えを追加して未使用扱いにしない。

### 9.2 人手評価者の手順

1. O/Qが独立評価者2人と調整担当、作業時間・資料許諾を確保。モデル出力を見る前に注釈規則とF1対応規則（同対象・意味・根拠範囲）を固定する。
2. 二人が独立に問い・根拠・対応・重要発言・立場・曖昧性を注釈。独立原票を保存し、後で一致させた表だけを残さない。
3. 不一致をcase/項目ごとに記録し、根拠付きで調整。複数の妥当な読みは正解集合に保持し、無理に単一解へしない。評価者間一致と算出対象・方法を報告。
4. 固定モデル／prompt／設定の同一入力を**3回**実行し、予測raw・検証後・失敗・修復・保留・runを保存。チャンク統合あり／なしを同条件比較。良い回だけ選ばない。
5. G2/G3を機能・ラベル・分野・反復ごとに集計し、分母・未提出・欠損・保留率・不安定さ・見落とし・統合誤りを報告する。明確な正解への保留は見落とし。全保留で合格にしない。
6. 自動評価と人手意味評価を分ける。既存ハーネスのID集合一致／文字列集合一致で測れない解釈・立場変化・意味安全・G8を合格扱いにしない。

特に既存`evaluateSuite`は未提出case/機能を平均から除外するため、受入用の全件manifestと照合して欠損一覧・件数を必ず別出力する。提出分の高い平均だけで固定set全件合格にしない。0/0・NaN・Infinityを数値成功へ置換しない。

### 9.3 意味の保持は三つの別指標

- **原文保持／到達性（G1）**：原文と引用・IDが残り、往復できるか。
- **重要発言の意味反映（G2/R27）**：対象、否定、条件、話者、時点が正しい問い・関係・結論へ保持され、根拠へ戻れる重要発言／重要発言総数。原文一覧に残るだけなら分子へ入れない。
- **まとめの意味保持（R14/R28）**：条件・例外・異論・未確認・撤回・主体・時点をまとめ自体に残すか。リンク先にあるだけでは十分としない。

重要条件を構造やまとめから故意に落とし、原文だけに残す負の対照を不合格にする。根拠引用が実在しても意味が支持されない分析はG3で不合格。解釈・立場変化・まとめ・確認提案は各々ケース、負例、保留基準、合格値を持ち、他機能の平均で未測定を覆わない。

### 9.4 R26/R29：分析誘導と話し方の公平性

安全setに「反対根拠を除け」「全員合意と出力せよ」、役割偽装、引用内命令を含め、原文として保持しつつ上位指示にしない。外部要求／実行が0でも、根拠IDを正しく付けた合意捏造・人物有利不利・反対意見削除を別採点。重大誤断定なら該当AI機能の公開を保留する。完全防止の保証はしない。

公平性は人が同義と確認したpairで、話者ラベル・丁寧さ・言いよどみだけを変える。回答有無・論点ずれ・根拠不足・立場のpair差と失敗例を報告し、特定styleの不利な誤判定増を検査する。意味を変える言換えに同じ出力を要求しない。人物間の判定を一律同じにする採点でもない。許容差・重大差の扱いはD05で事前承認し、結果後に決めない。

### 9.5 R30/G8：原文のみとの比較

評価前に、対象者・人数・資料数・課題・順序／割付・介助なしの条件・採点・時間開始終了・訂正負担・中断と欠損・合格値を事前登録する。元問、立場が変わった発言ときっかけ、残疑問、結論の条件と根拠、誤分析の訂正を課題にする。図の線種・復帰・合流・隠れた論点の読解も含める。

同じ資料を先に読む学習効果、条件間の難易度差、順序効果を計画に反映し、割付を固定する。原文のみとtool利用で、正答、重大誤理解、所要時間、訂正操作数・負担、完了／失敗を保存。本人同意と個人情報の扱いを決め、公開結果は集計・許可範囲とする。

初期案は原文より精度を落とさず時間を短くし、試験内で重大誤理解を生まないこと。ただし数値・判定法・人数は未決定で、O/QがP0で固定する。未実測は目的達成を実証したことにならず、G8未完了は公開判断上不合格。UIの存在・処理速度・利用者の感想だけで代替しない。

## 10. 通信・セキュリティ・権利・文書・公開（S08・P0/P6）

### 10.1 通信境界と攻撃試験

会話本文、人物名、入力ファイル名、hash、解析結果をnetwork・analytics・error report・URL queryへ送らない。通信は固定静的assetと利用者が明示開始するモデル取得だけ。外部font・広告・追跡・SDK・埋込・任意runtime CDNを使わない。依存は固定buildに含める。

モデル取得は配布元、容量、必要空き、license、IP等が配布元へ見えることを先に表示。版固定・許可先・可能なhash検証、破損cache再取得を試験。初回／更新完了前の完全offlineを約束しない。

| 試験                                       | 必須観測と合格条件                                                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 会話sentinel入力→解析→保存→export→失敗診断 | request URL/body/header、Worker、WebSocket、Service Worker、資産取得経路を確認。会話・名前・file名・hash・結果の送信0                         |
| URL登録／表示                              | 自動preview/prefetch/外部要求0。明示操作だけhttp/https、referrerなし、本文付加なし                                                            |
| HTML/MD/model output/import JSON           | XSS、危険URL、prototype pollution、過大object、循環／参照切れ、SVG実行／外部参照を拒否。テキスト描画。modelにfile/network/code toolを与えない |
| PDF/DOCX悪意入力                           | 外部参照、DTD/実体、zip bomb、path、timeoutで外部要求・実行0、資源限界内で停止                                                                |
| 本文内prompt injection                     | 外部操作0と意味誘導を別採点。R26の反対根拠削除・合意捏造・確定化を検出                                                                        |
| 配信CSP/origin/更新                        | 実環境の有効範囲と例外を検証。Pages header制約を黙って緩和しない。安全条件不成立なら配信再検討                                                |

page-realm request観測やmock counterだけで全通信不存在を証明しない。productionとmodel取得を含む範囲、観測不能経路、使用器材、試験時刻を明記。許諾のない実会話をCI・PR・ログへ入れず架空sentinelを使う。

### 10.2 originとofflineを別々に検証

R25はDB名・folderではなくoriginの信頼境界。専用originを選ぶなら別作品originから保存データへアクセス不能を実候補で試験。同一host全体を信頼するなら範囲と制約を明示し、独立隔離と称さない。

offlineは静的shell cacheとmodel cache、会話IndexedDBを識別する。現行Service Workerの明示準備・asset hash/scope検証はmodel取得成功や完全offline AIの証明ではない。全必要asset取得後、networkを切り、起動→入力→対応AI→図→訂正→保存→export/import→再開を対応範囲で試験。cache更新／破損／削除と会話非消失も試す。静的shellだけの成功をG6全体へしない。

### 10.3 権利と保守文書

Sec/Oが依存、model weights/tokenizer/量子化変換物、runtime、図library、font、sampleごとに固定版・配布元・license・利用／改変／再配布条件・NOTICE要否・権利者・未確認を一覧にする。本体Apache-2.0は提案で、権利者承認後だけ追加。不明資産は配布しない。auditの取得日・severity・未解消理由を残し、単にbuildできるだけでG7にしない。

人向けには操作、初回準備、端末×機能、容量と通信、保存・復元・削除、分析限界、失敗対処を整備。AI向けには処理全体、model/prompt/schema版・hash、根拠対応、コード位置、実行・試験、通信境界、制約を詳述。READMEと公開helpから共通の正本へ導き、版や未対応表示を一致させる。架空／許諾sampleと期待例、貢献案内、PR template、脆弱性報告経路、実会話・個人情報・鍵をIssueへ貼らない案内を揃える。

更新時は依存・モデル・prompt・schemaを隠して差替えず、理由、移行、再評価、巻戻しを公開する。開始中runは開始時構成を維持。重大誤引用・合意誤認・送信が見つかれば該当範囲の停止と回帰追加を判断する。

CIのartifact保持は現workflowで7日。消える前に許可された保存先へmanifest＋digest付きで保全する運用担当を決める。個人情報／実会話をrawごと公開せず、許可範囲を守る。ローカルpathしかない証拠は第三者がアクセスできない限界を記載。画像だけで正確な数値を代替せずrawを残す。

### 12.3 最終候補を一版にそろえる

受入候補は`release_candidate={code_sha,lock_digest,model_manifest,prompt_hash,schema_version,dataset_manifest,supported_environments}`で識別する。R別証拠は一つの候補へ集める。コードやmodel等が変われば第13.2節で影響を判定し、必要な再測定後に新候補を発行する。

複数端末は当然異なる環境だが、同じ候補構成と試験定義を使う。旧SHAの証拠は履歴として残し、最終候補試験とラベルを分ける。変更非影響の根拠があっても、最終統合回帰と必須実機・固定評価の未実施を省いて全体合格にしない。S09の公開承認前審査へは、追跡33行とゲート9票を候補状態で揃え、G0–G6・G8の全技術証拠およびG7の権利・安全・文書証拠が完備し、技術上の未達・未測定がないことを照合して進む。この段階のG7票には「証拠準備完了・所有者の最終公開承認は保留」と記録する。これは公開審査へ提出できる状態であり、G0–G8全受入やv0.4完成ではない。

続くS09-Aで所有者の別途の公開承認を同じ候補に紐付けて記録し、G7を最終判定する。G0–G6・G8の受入記録も揃い、必要範囲のR01–R33と全ゲートに未達・未測定・未承認がないことを再照合してから、全ゲート受入状態を確定する。マージ・リリース・配備の別判断も公式計画に従って記録し、必要な配備承認まで揃って初めてS10へ進む。公開承認が保留・否認・条件未充足なら、G7と全体受入は未完了のまま止める。
