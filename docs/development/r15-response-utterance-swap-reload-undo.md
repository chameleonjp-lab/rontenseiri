# R15 回答発言差替えの自動保存・再読込・Undo

問い版だけを別の問いへ付け替える先行ケースとは分け、通常UIで回答発言だけをU02からU03へ差し替える。製品コードを変更せず、旧・新両方の明示依存と独立したまとめを観測する限定回帰である。

## 通常UIで確かめる経路

`e2e/r15-response-utterance-swap-reload-undo.spec.ts` は、問いU01、旧回答U02、新回答U03、独立U04と、既存の問い版・応答・根拠を完全JSONの復元UIから取り込む。まとめAはU02だけ、BはU03だけ、CはU04だけを明示依存とする。問いの依存や関係エッジは置かない。初回だけ明示保存し、その後は通常の応答編集でU02のチェックを外し、U03を選択する。

AとBの両方だけが要再確認となり、Cの全フィールドは変化しない。応答は発言ID以外の全フィールドを比較し、問い版、種別、要求充足、根拠、反論先、注記、actor、元のtimeを保持する。原文・発言・関係と応答以外の推論graphも比較する。共有履歴のbefore/afterに旧新の発言IDが記録され、推論履歴の`response-updated`が同じ共有履歴IDを参照することを確かめる。

自動保存を待ってnative IndexedDBのreadonly transactionで保存状態・保存世代を観測し、再読込→最近の作業から再開→警告表示→完全JSONプレビューを比較する。通常の訂正履歴から1回Undoし、自動保存と2回目の再読込後に元の応答・全議題・推論graph・原文・発言・関係、警告解除、監査prefix・Undo targetとUndo枯渇を確かめる。

議題切替も保存対象の変更なので、再読込後のプレビューは、readonly DBの選択議題がAになり、履歴件数が期待値と一致し、画面が「現在版は保存済み」となるまで待ってから新たに生成する。保存中に生成された古いプレビューを待ち続ける方法ではない。既存のテスト全体30秒・poll上限10秒は延長せず、内容比較や警告のassertionは維持する。

## 証拠と限界

fixture作成はdomain APIを使うが、復元後の変更・保存・再開・Undoは通常UIのみ。ブラウザevaluateはnative IndexedDBのreadonly観測だけで、アプリstate注入やdomain/storage API呼出しはしない。選択議題・保存フラグ・保存世代・更新時刻は全体比較から除き、保存状態と保存世代の増加は別途検査する。完全JSONはプレビューを解析するもので、download/reimportの検証ではない。

1回答発言の差替え、2依存まとめ、1独立まとめ、1Undoだけを対象にする。問い版変更、問い分割、複数段依存、混合依存、多段Undo、保存途中reload、保存失敗・競合、全viewport、実モデル・意味品質、外部AI、性能は対象外。既存のdomain APIで問い版と発言を同時に修正する単体テストを、通常UIの証拠とは呼ばない。R15/G5やG0–G8の全受入、既知の500-node性能失敗の解消を主張しない。

追加ケースの初回実行は、U03を2議題に重複所属させたfixtureが`agenda membership invalid`で復元前に失敗した。U03の所属をBだけに直し、依存定義は変えていない。これは製品不具合や正常UI経路の失敗ではない。その後の1回は依存関係の準備との実行順序競合でVite起動前に失敗し、製品テスト未実行として区別する。どちらも証拠を上書きしない。

先行Draft #33の最終JSONプレビュー待機timeoutは原因未確定のまま独立した失敗証拠として保持する。この追加ケースに原因修正を混ぜたり、待機上限・assertionを弱めたりしない。実行ごとのSHA、終了コード、生ログ、JSON観測と失敗traceは別ディレクトリに保持し、公開CI、artifact内部照合、独立レビュー、マージの各状態を分けて記録する。
