# 欠けた応答関係を追加したときの要約の再確認

## 今回直すこと

[R15 / R17（計画 §19.3）](../requirements-and-development-plan.md#193-訂正保存出力)のうち、既存の原文・問い版・根拠はそろっているが応答関係が一つ欠けている場合を対象とする。利用者が通常の「問い・根拠」画面で問い版、回答発言、根拠、種別、要求充足、登録理由を明示して追加する。このとき影響する要約を要再確認にし、無関係な要約と既存グラフを保持する。

基点は #56 の `1074f11a1f396839a034177c6b3141d968334369`。#56 自体は変更せず、そのheadから分岐した一つの機能PRに製品修正、ドメイン・画面・保存回帰と本文書をまとめる。CI・マージ待ちはせず、通常pushとDraftのみ。外部AI、外部サービス、実行環境固有の依存は製品へ追加しない。

## 再現と最小修正

変更前の `linkResponse` は応答関係を保存しても、既存の依存伝播へ変更発言IDを渡していなかった。追加したドメイン回帰は、直接経路と根拠経由の両方で、依存先Aと下流Cの `needsReview` が `false` のままとなり失敗する。

修正は `src/domain/reasoning.ts` の `linkResponse` から、追加応答の `utteranceIds` を `commit` の既存の変更発言引数へ渡すことだけ。問い版全体や無関係な応答を変更扱いにはしない。既存の明示依存の固定点伝播、検証、共有履歴・Undoを再利用し、別の無効化処理は増やさない。種別から要求充足を推定せず、明示した旧版を現行版へ移さない。

## 一つのfixture・二つの依存経路

`tests/fixtures/manual-response-link.ts` をドメインと画面で共用する。選択議題Sは質問・回答を所有し、要約依存は空。別議題Aは回答発言への明示的な `summaryDependencies` を持ち、さらに下流の議題Cは二段の依存の到達先だけへ依存する。A/Cは依存先の発言を自分の所有発言に含めない。Bは独立した問い・応答・根拠を持ち、全オブジェクトを変更前と比較する。開始時は全議題 `needsReview=false`。既存の応答、非空根拠、主張、履歴を持ち、一つの欠けた応答関係だけを追加する。

直接経路では明示的な `relation.dependency` を二段たどる。根拠経路では既存根拠E1と主張I1を経て明示依存へ進む。直接経路に根拠経由の迂回路を置かず、単一の機能テスト群に両ケースをまとめる。質問版ID、回答発言ID、manualの出所、時点、種別answerと要求充足fulfilledを別々に保持する。

## ドメインと通常画面の検証

`tests/manual-response-link.test.ts` は、入力不変、A/Cだけの再確認、S/B不変、既存応答・根拠・主張の保持、理由付き共有履歴、通常Undoによる意味状態復元と監査保持を検証する。

`e2e/r15-manual-response-link.spec.ts` は直接・根拠経路それぞれを1440pxと390pxで実行する。対応するJSONを通常の復元UIで取り込み、初回保存後の変更はすべて通常UIで行う。関係追加→実際のautosave→native readonly IndexedDB観測→reload/最近の作業→表示・full JSON→通常UI Undo→autosave→二回目reloadをまとめて検査する。ブラウザ内でドメイン・保存モジュールをimportして状態を書き換えない。通信はlocalhost以外を記録して遮断し、外部要求がないことを確認する。

応答カードとfull JSONで関係の同一性を確認する。図では議題の再確認表示、一覧から開く共通の発言詳細では警告、振り返りではA/Cの警告とBの警告不在を検査する。関係追加後の原文・根拠は変更前と一致し、BはJSON表現も含めて不変である。共有Undoはグラフのスナップショットを復元し、プロジェクト履歴に追加イベントとUndoの完全なbefore/after、対象ID、理由を残す。グラフ内履歴を別途増やす契約とは混同しない。

## 証拠の保存と未検証範囲

変更前の回帰失敗、途中の検証失敗、修正後の結果を一意の実行ディレクトリへ残す。最終コミットのSHA、全単体テスト、関連ブラウザ回帰、format/buildの終了コードと生ログ、PlaywrightのJSON・添付を同じ証跡ルートへ保存し、PR本文に正確な結果を記録する。再実行成功で過去の失敗を削除しない。

図・一覧は現在、`ReasoningGraph.responses` の応答関係自体をエッジとして描画しない。関係の登録・編集は「問い・根拠」にあり、本変更はそれを図・一覧へ新設するものではない。したがって全画面に同じ応答エッジが描かれることは主張せず、共通の要再確認状態と原文到達性の検証に限定する。完全JSONの別コピー再取込みは #56 の範囲と重複するため今回は増やさず、追加・取消後のfull JSONと保存状態を比較する。

R15/R17/P3/P5全体、任意関係編集、再解析、意味品質、性能、実機、保存失敗・競合、公開品質ゲート、CI合格、レビュー承認、main統合の完了は主張しない。中央の受入ステータスは更新しない。公開headの正確なSHAでカメカメ・サポのレビューを別途依頼する。
