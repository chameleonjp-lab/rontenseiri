# R15：所属とは独立した要約依存の回帰確認

[要件 v0.4](../requirements-and-development-plan.md) の R15 に対する、ドメイン層のテスト4ケースと本文書だけのスライス。製品コード、CI、性能基準は変更しない。R15/G5 全体、G0–G8 の受入れを意味しない。

## 今回の追加

[テスト](../../tests/r15-summary-only-propagation.test.ts) は製品 parser と `createProject` から有効な6発言の fixture を作り、`validateProject` を通す。原文訂正 `reviseSource` と分類訂正 `reviseProject` の各APIを、2-hop関係の上流順・逆順で検査する（2操作 × 2配列順 = 4ケース）。

- 明示依存は U01 → U02 → U03。逆順では U02 → U03 を先に宣言するので、単一の関係走査だけでは U03 に届かない。
- 要約専用の議題は U04 だけを所属発言とし、`summaryDependencies: [U03]` を持つ。U03 は別議題の所属であり、要約専用議題の所属は到達集合に入らない。この条件自体もテストで固定する。
- U02 所属議題は `summaryDependencies: []` で要再確認にならず、U03 所属議題は同プロパティ未指定の既存仕様に従い所属を代用して要再確認になる。
- U05 への `dependency: false` と dependency 未指定の関係は伝播させない。無関係議題と既存の要再確認フラグを保持する。
- 全議題を深い比較で確認し、到達点・未回答・次の確認・その他の既存フィールドはフラグ以外を変更しない。関係全フィールドと入力プロジェクトの非破壊性も比較する。期待値は製品の伝播関数ではなくリテラルで記述する。
- 訂正理由と追加履歴、原文訂正の新しい版と旧版保持、完全JSON出力→再インポート後の意味状態・原文catalog・履歴保持を確認する。再インポートしたプロジェクトで直前の訂正をUndoし、元の意味スナップショットへ戻ることを確認する。Undo後も原文catalogと監査履歴は残り、全プロジェクトJSONが過去と一致するとは主張しない。
